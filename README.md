## RDB vs. Lakehouse: Key Differences

### Constraint Enforcement vs. Application-Layer Validation

The relational (`rdb`) schema relies on the database engine to enforce integrity:

- **Primary keys** prevent duplicate rows at the storage level.
- **Foreign keys** guarantee referential integrity — a `run` cannot reference a non-existent `event` or `model`.
- **NOT NULL** constraints prevent incomplete records from being committed.
- **Enum types** restrict fields like `run_type` to a defined set of values.

The Iceberg **lakehouse** schema has no engine-enforced constraints. Apache Iceberg is an open table format built on object storage — it provides ACID transactions, snapshot isolation, and schema evolution, but it does **not** enforce primary keys or foreign keys. This means:

- Uniqueness, referential integrity, and domain validation must be enforced at **write time** by the ingestion pipeline (e.g. a Spark job, a Flink pipeline, or an ETL service).
- Logical relationships are documented in the diagram comments (`%% Join intent:`) and in the data dictionary `references:` field, but they are advisory, not enforced.
- Duplicate detection and orphan checks become responsibilities of data quality tests (e.g. Great Expectations, dbt tests) run as part of the pipeline, not the storage layer.

This is the standard trade-off in lakehouse architectures: you gain horizontal scalability and cost-effective storage at the expense of moving integrity guarantees up the stack into application logic.

---

### Why Iceberg for FFRD Output Scale

The core output tables — `output_ts` and `output_grids_repo` — operate at a scale that is incompatible with a traditional relational database:

| Table | Estimated Scale |
|-------|----------------|
| `output_ts` | ~20,000–200,000 events × ~1,000s of elements × timesteps → **billions of rows** |
| `output_grids_repo` | One grid file per event per variable per run → **hundreds of thousands of Icechunk snapshots** |

Apache Iceberg addresses this scale through several mechanisms:

**Partitioning and file skipping.** `output_ts` is partitioned by `bucket(512, event_id)` and `run_type`. Iceberg maintains a manifest of which data files cover which partition values, so a query for a single event's time series skips all unrelated files entirely — no full-table scan.

**Sort ordering.** Each data file is sorted by `event_id, element_id, variable, ts`. This means a read for a specific element's full time series within an event hits a narrow file range, making the access pattern as efficient as a clustered index in a relational database.

**Snapshot isolation and time travel.** Every write produces an immutable snapshot. A hotfix rerun produces a new snapshot, not an overwrite. Old snapshots remain queryable for audit and comparison, directly supporting the version traceability requirements in the user stories.

**Schema evolution without rewrite.** Adding a column (e.g. `ingest_ts`, `source_system`) does not require rewriting existing data files. This supports iterative schema development as the model matures.

**Icechunk for gridded outputs.** Gridded outputs are stored in [Icechunk](https://icechunk.io) repositories — a chunked array store designed for Zarr/NetCDF-style data with Iceberg-compatible snapshot semantics. `output_grids_repo` stores metadata pointers (repository URI + snapshot reference) rather than blob data, keeping the Iceberg table lean while the heavy array data lives in the chunked store.

## Materialized Views

The [derived domain](lakehouse/derived.mmd) defines seven materialized views that pre-aggregate the high-volume source tables for common query patterns:

| View | Source | Purpose | Stories |
|------|--------|---------|---------|
| `mv_peak_output_by_element` | `output_ts` | Peak value per element per run | 15, 24, 28 |
| `mv_event_variable_stats` | `output_ts` | Mean/max/min/std across elements per event | 6, 32 |
| `mv_aep_frequency_stats` | `output_ts` + `events` | Frequency statistics (p10/p50/p90) per AEP band | 11, 28, 31, 32 |
| `mv_gage_model_comparison` | `output_ts` + `obs_ts` | Observed vs. modeled peak bias per gage | 15 |
| `mv_run_performance` | `run_catalog` + `run_resources` | Duration, cost, and status per run | 2, 3 |
| `mv_basin_cost_rollup` | `run_resources` + `run_catalog` | Monthly cost and utilization rollup per basin | 4 |
| `mv_conformance_summary` | `models.metadata_json` | Conformance check pass/fail per model version | 5 |

These views are **not source-of-truth** — they are regenerated after each batch commit and serve as read-optimized accelerators. Without them, answering questions like "what is the 100-year peak flow at this junction across all realizations?" would require scanning billions of `output_ts` rows at query time.

## Gridded Data — Icechunk Repositories

Gridded (raster) outputs from flood models are stored in [Icechunk](https://icechunk.io) repositories rather than as relational tables. Icechunk is a chunked, cloud-native array store built on [Zarr](https://zarr.dev) conventions that provides snapshot semantics compatible with Iceberg. Metadata pointers live in the relational schema (`observed_grids` and `output_grids` tables); the actual gridded data lives in three long-lived repos.

**Source repositories:**
- `observed_precip`: Real-world NOAA AORC meteorology (precip, temperature) indexed by `storm_id`
- `hms_excess_precip`: Synthetic HEC-HMS excess precipitation, merged per event, indexed by `event_id`
- `ras_output`: HEC-RAS peak flood depths and velocities, merged per event, indexed by `event_id`

**Derived repositories:**
- `ras_recurrence_grids`: Frequency grids (10, 25, 50, 100, 250, 500-yr RI) computed per realization
- `ras_recurrence_ensemble_stats`: Cross-realization uncertainty (mean, median, 5th/95th percentile) at each RI

For full details on repository structure, xarray schemas, computation workflows, and use cases, see [grids/icechunk.md](grids/icechunk.md).
